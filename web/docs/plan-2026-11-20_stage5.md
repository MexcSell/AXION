# Stage 5 Implementation Plan: real sign-in, database, mission API, live events

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the browser-only DEMO data for sign-in, users/devices, missions, approvals and notifications with a real server and database. Every user then sees the same data, it survives restarts, and permissions are checked on the server. Agents still do **not** execute anything.

**Architecture:** A new Fastify API (`/home/luca/AXION/server`, 127.0.0.1:5191) stores data in a new PostgreSQL database `axion` on the PostgreSQL 16 server that is already running. The web app keeps its zustand stores as the view model. In `api` data mode their actions call the API, and their state is filled from one snapshot plus a live event stream (SSE). Zod schemas in `/home/luca/AXION/shared/contracts` are imported by both sides.

**Tech Stack:** Node 24, TypeScript, Fastify 5 (+ `@fastify/cookie`, `@fastify/rate-limit`, `@fastify/multipart`), `pg`, Zod, `@node-rs/argon2`, Vitest, plain-SQL migrations with up/down files. Web: existing React 19 / Vite 8 / zustand.

**Spec:** `update/2026-11-20/AGENT_COMPANY_OS_MASTER_DESIGN_AND_CLAUDE_CODE_PLAN_2026-11-20.md` §10.5–10.6, §11, §12, §13, §15 "Stage 5", **as amended by** `update/2026-11-20_u1.md` and the owner's u1 answers (in `web/PROGRESS.md`). Where the two disagree, u1 wins (see "Deviations").

## Deviations from the spec's Stage 5 text (because of u1)

- **No budgets, cost, usage ledger or `budget_snapshot`:** u1 removed all funds. The `BUDGET_HARD_LIMIT` error is dropped.
- **Sign-in uses name + password, not invitations.** The first account becomes admin. Later accounts and every new device wait for an admin. Passwords are hashed with **argon2id** and no raw password is ever stored.
- **Roles are `admin | member`.** Mission rights: the owner and admins see private missions and everyone sees shared ones. A shared mission is **read + write** for everyone who can see it, but only its owner or an admin may flip `shared`.
- **One company:** a single `tenants` row. `tenant_id` is still on every record and checked in every query, so multi-company stays possible and is tested.
- **No tables or endpoints** for the removed pages: Governance, Knowledge, Evolution, Usage, Browser Studio.
- **TanStack Query and React Hook Form are not added:** the existing zustand stores become API-backed instead, so all views stay unchanged.
- **Still DEMO after Stage 5** (they move later): mission conversations and chat dock (Stage 6), agents, lineage, models and VMs (Stages 6/9), Job Search, News, results/artifacts (Stage 8).

## Global Constraints

- Every listener binds to **127.0.0.1** only: API **5191**, web dev **5190**, preview **4190**. No public port, no Docker.
- The API prefix is `/api/v1`. Every error body is `{code, message, correlationId, retryable, fieldErrors?}`, with no stack traces, paths or SQL.
- Never read or modify the other databases on the cluster. Only `axion`, `axion_test` and `axion_restore_check` are ours.
- Mission execution stays **disabled**: there is no job queue and nothing calls a model or a browser. A guard test proves it.
- Clients never set a status directly. Only the server's state machine changes it (spec §10.6).
- Secrets live in `server/.env` (mode 600, git-ignored), never in the repo, the logs or API responses.

## Review Focus

1. **Account changed while signed in:** if an admin disables or rejects a user, or blocks a device, that user's next request gets 401 `SESSION_REVOKED`, their open event stream closes, and the UI returns to the sign-in screen. Test in Task 2.
2. **Mission made private while another user has it open:** their next read gets 404, they receive no more events for it, and the UI leaves the mission with a toast instead of crashing. Test in Tasks 4 and 9.
3. **Server restart or a dropped connection mid-session:** a "reconnecting / stale" badge appears, the client resumes with `Last-Event-ID` with nothing lost or duplicated, and unsent drafts, open dialogs and scroll position survive. Test in Tasks 5 and 9.
4. **Names that only look different:** `"Luca"`, `" luca "` and `"LUCA"` are one account (trim, collapse spaces, NFC, unique on lower case). The wrong password for an existing name never creates a second account. Test in Task 2.
5. **Odd uploads:** a 0-byte file, a file over 25 MB, a file whose extension doesn't match its content, or a name with `../` is rejected with a clear message. Nothing is written outside `server/data/uploads/`. Test in Task 4.

### Task 2: Sign-in, users and devices

**Files:** `server/src/auth/*`, `shared/contracts/src/auth.ts`, `server/test/auth.test.ts`.

**Interfaces:**
- `POST /auth/connect {name, password, device:{name,kind,browser}}` → `200 {state:'signedIn', me}` or `202 {state:'waiting', reason:'user'|'device'}`. Errors: `401 WRONG_PASSWORD`, `403 USER_DISABLED|USER_REJECTED|DEVICE_BLOCKED`. It sets the cookies `axion_sid` (HttpOnly, SameSite=Strict, 30 days) and `axion_dev` (device id, 1 year). While waiting it sets only `axion_dev` plus a short `axion_wait` ticket.
- `GET /auth/wait` → `200 {state:'signedIn', me}` once approved. The client polls it every 3 s, and the `auth.approved` event also triggers it.
- `GET /me`, `POST /auth/logout`, `PATCH /me {name?, avatar?}`, `POST /me/password {current, next}`.
- Admin: `GET /users`, `POST /users/:id/{approve|reject}`, `PATCH /users/:id {role?, status?}`, `POST /users/:id/devices/:did/{approve|block}`, `DELETE /users/:id/devices/:did`.
- The "first account becomes admin" check runs under `pg_advisory_xact_lock(1)`, so two simultaneous first connects can't both become admin.
- `npm run admin:approve-device -- <name>` is a server-side recovery command: it approves that user's newest pending device and writes an audit row (see D4).
- `normalizeName(raw): {display, key}` in `auth/names.ts` (trim, collapse spaces, NFC; key = lower case).
- `requireUser(req)` and `requireAdmin(req)` hooks. Every write needs the header `X-CSRF` equal to the session's csrf (returned in `me.csrf`).

### Task 3: Mission tables and the state machine

**Files:** `migrations/0002_missions.*`, `server/src/missions/machine.ts`, `shared/contracts/src/missions.ts`, `server/test/machine.test.ts`.

**Interfaces:**

- `USER_ACTIONS = ['start','pause','resume','cancel','retry','archive','restore']`: the only actions the API accepts from people.

- **Create path:** `POST /missions` stores the mission as `draft`. In the same transaction it runs `submit` (→ `queued`) and then `plan` (→ `planning`), and the staffing simulation starts. This matches today's UI, where a new mission appears in "planning" and staffing begins at once.

- UI mapping (in contracts): `waiting_approval`→`waiting`, `retry_queued`→`queued`. New badges for `queued` and `canceled`.
- `restore` returns an archived mission to the status it had before it was archived (stored in `presentation.preArchive`).

## Rollback

1. Switch the web to demo mode (`VITE_DATA_MODE=demo` or `?data=demo`). The UI works exactly as it does today.
2. Run `cd server && npm run migrate -- down 0` to empty the schema, or restore a dump with `db-restore-check.sh`.
3. If the owner wants it all gone: `dropdb` only `axion`, `axion_test`, `axion_e2e` and `axion_restore_check`, then `drop role axion`. No other database or service is affected.
4. Every task is one commit on `main`, so `git revert` undoes it.

## What Stage 5 does *not* do

There is no real agent work, no model calls, no browser automation, no mission conversations on the server, and no systemd units or public access (those are Stage 12). The other databases on this machine are not touched either.
