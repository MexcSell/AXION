## Patterns taken from the subnet-scout backend (read only, `/home/thomas/subnet-scout/backend/app`)

subnet-scout has no agent versions and no agent-authored mission threads, so Stage 6 designs those from the spec. Its smaller rules are adopted as follows.
- **Cycle check by walking the manager chain** (`organization.py` `_set_line`/`chain()`: seen-set, limit 64) applies to `org_edges` and mission instance parents. It also rejects self-management.
- **Authorship is fixed by the server**, with no role field in the API (`gm_chat.py`). In our POST bodies, the role is ignored.
- **No fake replies.** When there is no model, subnet-scout writes an honest system message instead (`gm_chat.py` 201–204). This is E5/E6.
- **Uploads are checked at send time:** they must belong to the sender (`gm_chat.py` 170–176).
- **Paging uses an id cursor**, newest first (`gm_chat.py` 120–127). Ours uses the per-thread `seq`.
- **Retry and reassign are user actions:** they return 409 while the task is running, and each writes audit and history rows (`task_lifecycle.py` 922–995). The failed attempt is kept.
- **Delegation authority** (`organization.py` `may_delegate`): the simulation only delegates down its own mission tree. A person may reassign to any instance in the mission.
- **Metrics provenance:** the score is `null` when there are fewer than 5 pieces of evidence (`MIN_EVIDENCE`), the window is 90 days, and the evidence count is shown (`organization.py` 1212–1263). `provenance = {source, sample, window:'90d'}`, and a measured value with `sample < 5` is shown as "not enough evidence".
- **Org change requests bound to a hash and applied once** (`og_requests`) are noted for Stage 11, not built now.

## Global Constraints

- **Never touch the live database.** Implementers must not run `npm run dev`, `npm run migrate` or `demo:*` with `DATABASE_URL` (`axion`). They must not stop, restart or call the API on **127.0.0.1:5191** or the Vite server on **5190**, and must never sign in against 5191. Use only Vitest (`axion_test`, a schema per file) and `web/scripts/api-e2e.sh` (API 5192 + Vite 5193, `axion_e2e`). Only Task 8 migrates the real database, and only after `db:backup` and `db:restore-check` pass.
- Every listener binds to 127.0.0.1. The prefix is `/api/v1`. Errors use the Stage 5 envelope `{code, message, correlationId, retryable, fieldErrors?}`.
- **The server takes identity from the session.**
  - The author of every human message is `human:<session user id>`. A `from` sent by the client is ignored.
  - A person can never write as an agent or as the system, nor read or write a thread they cannot see. An invisible mission, thread or channel returns **404**.
- **Append-only tables:** `agent_versions`, `mission_delegations`, `task_attempts`, `messages`, `message_receipts` and `org_edges` reject UPDATE and DELETE through a trigger, as `audit_events` does.
- **Execution stays disabled.** The Stage 5 execution-guard test is extended to the new modules: no `child_process`, `playwright`, `anthropic`, `openai` or `fetch` to model hosts.
- **Simulated content only on `demo=true` missions.** It is always stored with `simulated=true` and always tagged *Simulated* in the UI.
- Demo mode (`?data=demo`) behaves exactly as today, and `web/scripts/verify-all.sh` stays green.
- Commit once per task on `main`. Before each task, check `git log` for commits made by someone else and note them in the ledger.
- After Task 8: **STOP**, and ask "Stage 6 is complete. Do you approve Stage 7?" Stage 7 starts real browser automation.

## Review Focus

1. **Forged authorship:** a client posts `{from:'gm', kind:'report'}` into a mission thread. The message is stored as `human:<me>` with kind `command`, or rejected with 422; it is never stored as an agent message. Posting to another user's `gm:`/`agent:` channel id → 404. Test in Tasks 3 and 6.
2. **A mission made private mid-conversation:** the other user's next `POST /threads/:id/messages` → 404, and their stream stops receiving that mission's `conversation.*` events. Test in Task 3.
3. **Agent upgraded while a mission runs:** a PATCH that changes skills creates v(n+1). Existing instances still report v(n), newly staffed instances get v(n+1), and the UI shows the version on each instance. Test in Tasks 1 and 2.
4. **Long threads:** a thread with 5,000 messages loads the newest 50. Scrolling up fetches older pages with no duplicates and no jump, and the minimap still works. Test in Tasks 3 and 4.
5. **The owner signs in during this stage:** missions seeded under the Stage 5 schema get instances, delegations, tasks and threads from the startup backfill. Running the backfill twice changes nothing (same row counts). Test in Task 2 and again on the real database in Task 8.
