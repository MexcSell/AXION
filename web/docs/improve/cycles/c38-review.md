## Important

**I1. Model-family rule splits one vendor into several families, so self-judging gets through.**
`server/src/tasks/review-rules.ts:11` (`/^[a-z]+/` on the free-text model, `agents/versions.ts:29` allows any 1-120 char string).
Traced by hand through the regex:
- `gpt-4o` -> gpt, `o3` / `o1-mini` -> `o`, `chatgpt-4o` -> chatgpt, `openai/gpt-4o` -> openai: four spellings of OpenAI.
- `gemini-2` -> gemini vs `gemma-3` -> gemma (Google); `mistral` vs `mixtral` / `codestral`; `claude-3-5` vs `anthropic.claude-...` (anthropic) or `us.anthropic.claude...` (us).
- `my-claude-proxy` -> `my`.
Two agents of one vendor can therefore review each other, which is exactly what the rule exists to stop (2404.13076). The opposite collision also exists: `text-davinci` vs `text-bison` -> both `text`; `o` is a one-letter bucket. "claude-opus vs claude-haiku same family" and "gpt-4o vs gpt-4.1 same family" do hold. Whitespace and empty/`5-turbo` are null and treated fail-closed (good: `independence()` refuses a null family, and the DB CHECK needs both non-null).
Fix: a small explicit alias table (o1/o3/o4/chatgpt/openai -> openai, gemma/gemini/palm -> google, ...), strip provider prefixes (`x/`, `us.anthropic.`), and treat a name matching no known vendor as null (fail-closed) rather than "its leading letters". Add the cases above to `task-review-rules.test.ts` (today it only tests claude/gpt/whisper/llama and the empty cases). Not exploitable over HTTP today, since no route names an agent reviewer, but the service and the DB are built for it and the rule is the central claim of the cycle.

**I2. A review is accepted for a task in any status, and then counts as "verified".**
`server/src/tasks/reviews.ts:44-52` (`visibleTaskRow`, no status condition), `recordReview` at about `:113`; scorecard `scorecard.ts` (`nTaskVerified` has no task-status condition); UI `missions.tsx` Review button shown for every task (the drawer only hides Cancel/Retry on status).
A pending, running, failed or canceled task can be accepted with a URL as evidence and is counted in "Tasks verified by review". Every fixture task in `task-reviews.test.ts:27` is hard-coded `'passed'`, so no test covers this. Decide and enforce: either only `passed` (or `needs review`) tasks are reviewable (`canReview` code e.g. TASK_NOT_REVIEWABLE, plus scorecard excludes accepted reviews whose task is no longer passed), or document that a pre-completion review is intended. Note the later Retry of a failed task after an accepted review is also not reflected (latest review still wins).

## Minor

- **M1. Reassign / re-pin.** `reviews.ts` `producerOf` derives the producer only from the CURRENT owner at review time, and stores it. Answer to the brief: a reassign after a review cannot change the stored row or its meaning (producer/principal/family are frozen; the scorecard compares the stored `producer_id`), and a human reviewer cannot become a producer (tasks have only agent owners), so the "review, then reassign so the reviewer becomes the owner" attack does not work for people. It is a latent gap for agent reviewers: an agent that produced an earlier attempt and was then reassigned away is no longer "the producer" and could review (reviewer != current owner). The attempts' actors are not consulted although the brief said "assignee / attempt actor". Cheap fix: also exclude agents that appear as owner of any earlier attempt/delegation of the task.
- **M2. Scorecard excludes the mission owner by the CURRENT owner** (`scorecard.ts`, `owner.get(r.missionId)`) and ignores the stored `principal_id`, which the loader (`company/routes.ts:37`) does not even select. If ownership ever changes the count shifts retroactively. Use the stored principal.
- **M3. SINCE_STAGE5_WRITES not extended** (`server/test/security.test.ts:34`). That list drives the per-route CSRF tests (`:256-271`: missing X-CSRF, wrong X-CSRF, cross-site Origin) and an existence check on the route table. The implementer relied on the global hook and api-c38's 403 flow, but the new write route has no per-route CSRF test, which every other write route since stage 5 has. Add `['POST','/api/v1/tasks/:id/reviews']`. (The LIMITED_ROUTES expectation was extended, that part is fine.)
- **M4. "Verified" chip vs "Independent review".** `web/src/data/roles.ts:96` still labels a `passed` task "Verified" (violet), next to a list that says "No review yet. A task counts as verified only after ..." in the same drawer. That is the confusion the brief warned about, and it contradicts the new meaning of verified (spec invariant 5). Rename to "Passed" (the report admits it left it, citing text-matching checks). Also the drawer copy "complete when ... an independent verifier accepts the evidence" in api mode and the hard-coded "Tester-01 (independent)" remains in demo mode only (acceptable).

Scorecard tests.** The two changed assertions are legitimate, not loosened: `scorecard.test.ts:35` still asserts the exact ordered key list, with the 2 new keys appended after the 8 old ones, so old rows keep order/meaning; `scorecard-trend.test.ts:46` only adds `|| unit === 'tasks'` to a clause that already accepted `missions` (counts, previous 0). `FLAT.tasks = 0` mirrors missions.
