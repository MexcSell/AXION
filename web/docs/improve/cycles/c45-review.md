## Findings

### Minor (confirmed by running)
1. **Raw SQL can revive or shorten an expired lease and can release an unexpired one.** `0035_system_jobs.up.sql:55-58` (leased -> leased) and `:65-70` (leased -> queued/dead/canceled) never look at `lease_expires_at`/`now()`. Confirmed: `update system_jobs set lease_expires_at = now()+interval '1 day'` on a leased row succeeds, as does moving the expiry into the past; `leased -> queued` with token+1 on an unexpired lease succeeds. Only succeeded/failed check expiry. The store is correct (`LIVE` uses `> now()`), so only a hand-written UPDATE does this. The report's "leased row ... only legal edges" claim holds for ownership, not for the clock. Fix: in leased -> leased require `old.lease_expires_at > now()` (heartbeat only while live) or document that the trigger allows an operator to touch expiry; in the release branch require `old.lease_expires_at <= now()` unless the caller is failJob/ack (they need it, so that edge needs a different rule, probably leave as is and document). Tests rely on raw expiry changes, so this was a deliberate trade-off, but say so.
2. **No INSERT guard.** Confirmed: raw INSERT of a row directly as `leased` (owner, token 1, attempt 1) or as `queued` with `lease_token=99, attempt=2` succeeds. A job can therefore appear mid-life without a claim. CHECKs only cover shape. Fix: a `before insert` trigger forcing `status='queued', attempt=0, lease_token=0, cancel_requested=false`, or CHECKs on that. Low risk now (nothing outside `src/jobs/` inserts; the api-c45 e2e fixture does raw inserts).
3. **Queued -> canceled needs no `cancel_requested`.** Trigger line 59-60 accepts `status='canceled'` from queued with the flag false (confirmed). Store always sets it. Harmless; inconsistent with the leased branch which demands the flag.
4. **Token argument is not validated in Node.** `completeJob/heartbeatJob/failJob/acknowledgeCancel` with `token` 1.5, NaN or 2**70 throw a raw Postgres `invalid input syntax for type bigint` instead of returning `stale_token` (confirmed; -1 correctly gives `stale_token`). A worker bug becomes a 500/throw rather than a refusal. Fix: `Number.isSafeInteger(token) && token >= 0` guard returning `stale_token`. Related: `lease_token::float8` loses exactness above 2^53 (unreachable in practice).
5. **`claimJob` / `reclaimExpired` without `tenantId` span all tenants** (`store.ts` claim `$4::text is null`, reclaim `$1::text is null`). Safe today: confirmed by grep that only `src/jobs/` and tests reference them, and the static test enforces it. But the safe-looking default is the dangerous one: a future route that forgets `tenantId` crosses tenants, and `reclaimExpired` then writes audit rows for other tenants. Recommend fail closed: require `tenantId` or an explicit `scope: 'all-tenants'` literal. Not blocking because it is worker-level by design and documented.
6. **Static "no execution" tests are bypassable** (`jobs.test.ts:511-533`). They are regex greps over `server/src/**/*.ts`: a dynamic `import('../jobs/' + 'store')`, a re-export through another name, any file under `server/scripts/` (not scanned), a `while(true)`/promise-sleep loop (not matched by the timer regex), or `app.route({method:'POST'})`/`fastify.post(` (not matched by `app\.(post|put|patch|delete)\(`) all pass. They catch accidents, not intent. Acceptable for a records-only cycle; the real guarantee is review plus the fact that nothing instantiates a worker. Confirmed by reading the regexes, not by writing a bypass.

### Minor (plausible, not run)
7. **Spurious `null` from `claimJob` under contention.** `select ... limit 1 for update skip locked` in a READ COMMITTED CTE can pick a row that a concurrent committer changed after the snapshot, fail the re-check, and return no row although other queued jobs exist. Harmless (the worker polls again) and the 20-claimer/50-job test still passes, but a worker must treat `null` as "try again soon", not "queue empty".
8. **Audit under c31.** `audit()` in c31 takes the global events advisory lock then a per-tenant lock, held to commit. `reclaimExpired` holds row locks on every expired job while it audits dead rows one by one, inside one transaction; with many dead-lettered jobs across tenants this serialises against every other emitter and could hit the 5 s `lock_timeout`, rolling back the whole reclaim. No deadlock is expected (global lock is first, one global order), but batch size is unbounded: add a `limit` to the reclaim batch. Merge is textually clean and `audit(c, {...})` keeps the same signature, so job.enqueue/cancel/dead will chain after merge; the integrator should still run the c31 chain-verify test after merging.
9. **`now()` is transaction start inside `failJob`/`reclaimExpired`/`requestCancel` transactions** (statement start for the single-statement ops). Lock waits up to 5 s mean a `failJob` can succeed up to that long past real expiry, but only if nobody reclaimed (a reclaim bumps the token, so a stale holder is still fenced). No double-owner path found: heartbeat `>` versus reclaim `<=` are complementary on the row version each locks, and skip-locked/row re-check handles the interleavings. The stress test found none.
10. **UI**: the `JobRecords` panel sits above the existing mock `Queues` content; the page now mixes real counts (zero) with prototype queue data. The panel says "Records only" and has empty state and `?`, but a reader may be confused by two queue views. Consider a one-line DEMO label on the old queues block. Ran at 1366x768: no overflow.

## Answers to the focus areas
1. Fencing: token bumped on claim, reclaim, retry, dead, cancel-ack (trigger enforces +1; fail for good and succeed keep the token, both terminal). Stale token cannot heartbeat/complete/fail (`LIVE` predicate has token and `> now()`; `failJob` locks with `for update` using the same predicate; stress test clean). `FOR UPDATE SKIP LOCKED` is in the same statement as the update (claim CTE, reclaim subquery). Assumes READ COMMITTED (default); under REPEATABLE READ concurrent updates would raise serialization errors rather than double-own.
2. Trigger: terminal rows cannot change; token and attempt cannot decrease (confirmed); a leased row cannot lose owner, expiry or heartbeat (CHECKs, confirmed `nullHeartbeat`); owner change refused; payload_ref bounds (513 chars, shell text, empty) refused. Gaps are findings 1-3.
3. Time: every lease comparison is SQL `now()`; `Date` appears only in the `checkedAt` response field and in `iso()` formatting. Nothing lease-related is computed in Node (the `secs()` bound check is a number range, not a clock).
4. Tenancy: id-addressed ops all require `tenant_id`. `/operations/queues` and `queueSummary` filter on the session tenant (a lane test with two tenants confirms no leak). Admin only via `requireAdmin` (member 403 confirmed in e2e). No write route: confirmed, the only job reference outside `src/jobs/` is the `queueSummary` import in `ops/routes.ts`.
5. No timer/interval/worker in `src/jobs/` (read all three files). See finding 6 for test robustness.
6. Audit: enqueue (only when created, not on idempotent replay), cancel, and dead (fail and reclaim) write audit rows inside the job transaction, so they roll back together. See finding 8 for c31. Note `acknowledgeCancel` and cancel-by-reclaim write no audit row (only the request does); acceptable.
7. UI: empty state, `?` help `ops.jobRecords`, read-only chip, no write controls, a11y label on the refresh button, fit OK (e2e). Not manually audited with a screen reader.
8. Suites: tsc clean; vitest 38 files / 649 tests pass; e2e 10/10.
