# c63 report: organisation-level failure learning (R3-8), lane w61, migration 0047

Branch `c63-failure-learning`, from `c60-attribution-otel` at df8c17e. Ports 11190 to 11193, e2e DB axion_e2e12. Records, counts and review rows only: nothing executes, no model call, no playbook is ever activated by this code.
Load average is printed next to every timing (the machine was at 15 to 22 throughout).

**Evidence honesty.** D2 (silent failures, mostly caught by humans) is one author on one runtime. It motivates the detection-channel field and gives no rate. D1's 24% is not used anywhere. The "found only by a person" share is a count of what taggers recorded here, not a measured rate of anything, and the help text says so.

## What was built
1. **Detection fields (item 1).** Migration 0047 adds six nullable columns to `failure_tags`: `detection_channel` (test, audit, human_review, other_agent, reported_later), `detected_after_seconds`, `mechanism` (instructions, context, tool, reasoning, handoff, environment, other), `control_expected` and `control_caught` (test, review, approval, monitoring, validation, none, other), and `detection_note` (1 to 300 characters). CHECK constraints: closed lists, no negative time, a time needs a channel, "other" needs a note. The c33 guard is replaced so the decision UPDATE cannot change any of them (raw UPDATEs are refused, tested); the down migration restores the 0028 body.
   - `detected_after_seconds` is **never accepted from the caller** (400, strict body). It is computed in SQL in the tag's own transaction as `now()` minus the stored failure time, clamped at 0, only when a channel is given. Failure time = finish time (else start time) of the latest failed attempt of a task, or of the tagged failed attempt. A task that failed with no attempt row, a message and a mission have no stored failure time, so the value stays null and counts as missing.
   - **Limits, stated:** it measures to the moment the tag is recorded, so a failure tagged a week after a person noticed it shows a week. The fields are written at tag time only (the row is append-only); there is no "add later" route (concern 3).
   - Value lists live in `shared/contracts/src/failures.ts` with a label and a help sentence each. They are AXION's own words (no source defines them; D1 is CC BY-SA and was not copied).
   - The counts view (`GET /company/failure-modes`) gains `detection`: for each of the five fields how many confirmed tags have it and how many lack it (count and share, never hidden), confirmed tags per channel. Its window bound is now SQL `now()` (it was the app clock through `windowOf`).
   - OTel export: the five enum or number fields export as `axion.failure.*` attributes (fixed vocabulary, so they are not free text); `detection_note` is content, so it is a `_ref` pointer by default. Mapping table, doc and content list updated; the c60 mapping and export tests pass.
2. **Recurrence rule (item 2).** `server/src/failures/patterns.ts`. A confirmation that completes the pattern calls `evaluateFailurePattern` inside the same transaction: same mode, at least **3** failures, at least **2** departments, last 30 days. It opens one row in c41's `lesson_candidates` through c41's own `proposeLesson` (kind `agent`, proposer `failure-pattern-review`), with the failures as `failure_tag` sources (c41 caps sources at 10, so the newest 10), and records the link in the new append-only table `failure_pattern_candidates` (mode, window, all failure counts, department names, every task id and tag id, `origin = system_failure_pattern`). c41's table and guard are not touched.
   - **What counts:** confirmed tags only, non-DEMO non-deleted missions, tag creation inside the window (SQL `now()`), distinct failed **tasks** (a task and its attempt with the same mode are one failure; message and mission tags are not counted), department = `agent_definitions.dept` of the task's **current** owner (owner instance's agent, else `owner_agent`). A failure with no owner agent has no department and is left out.
   - **One open candidate per pattern per window:** a lock named for (tenant, mode, window) through `locks.ts`; while one is `proposed` nothing else opens; after a person decides it, a new one opens only if a qualifying tag was confirmed after the previous candidate was made.
   - **Agent:** c41 playbooks are per agent and `agent_id` is NOT NULL, but a cross-department pattern has no single owner. The candidate goes to the agent that owned most of the failures (lowest id on a tie). A convention for the reviewer to overrule by rejecting (concern 1).
   - **No playbook:** the module contains no playbook write (a test greps for it), and tests show zero rows in `playbooks` after every scenario, a member gets 403 and the system cannot decide (c41 CHECK), while a person's accept through c41's route still works.
   - `GET /company/failure-patterns` (administrators only) lists the patterns with the candidate's status and `derivedBy: system_failure_pattern`.
3. **"Found only by a person" (item 3).** Part of the `detection.humanOnly` block: `humanReview`, `withChannel` (the denominator), `missing`, `share`, `minN` = 5, window. The share is the share of confirmed tags **with a recorded channel** that say `human_review`; it is null below 5 such tags (the null rule is applied to the denominator actually divided by, so seven confirmed tags with four channels still give null). The dialog shows it with n, the window, "needs 5" while null, the not-recorded count and share, and a `?`.
4. **UI (item 4).** The Tag a failure dialog (now size xl, because lg overflowed 1366x768) gets four optional selects in the left column under the modes: Found by, What failed, Meant to catch it, Did catch it. Each field has a `?`, each chosen value gets its own `?` (help entries exist for every value of every list), "something else" shows a required note field and the Tag button waits for it. Tags in the list show the recorded fields and the computed time ("after 2 h 5 min" only when computed). Help entries: `failure.detect*`, `failure.humanOnly`, `failure.missing`, `failure.patterns`.
5. **Contracts (item 5).** `FailureTagDto` fields, `FailureDetectionDto`, `FailurePatternDto(s)`, enum lists in shared contracts; registry (`GET /company/failure-patterns`, admin), validators for every new field and route, and coverage-run calls that fill the new fields (six confirmed tags with a channel across two departments, one carrying every field and an "other" note). **No allowlist line**: `exercised.ts` and `allowlists.ts` are untouched.

## Concerns
1. **For the integrator: c59 origin class.** c59 (branch `c59-origin-records`, migration 0044) adds `origin_channel` and `origin_class` to `lesson_candidates` and an insert trigger that defaults an agent-kind row to `agent_output` / class `agent`. c63 inserts its candidate through `proposeLesson` with kind `agent`, so after the merge it would be classed as an agent's own output. These rows are derived from stored tool records, so the one call site in `server/src/failures/patterns.ts` (`proposeLesson(c, {...})`) must pass `originChannel: 'tool_output'` (class `tool`, the lowest). I did not touch `lesson_candidates` or its guard, so 0044 and 0047 do not collide (0044 replaces `lesson_candidates_guard`; 0047 does not). Until then the system origin is carried by the `failure_pattern_candidates` row, the `System-derived from tool records, not written by a person.` text prefix and the `failure_tag` sources. The candidate DTO and `/lessons` do not show `derivedBy` (that would edit c41's and c59's DTO); only `GET /company/failure-patterns` does.
2. **Agent choice.** A cross-department pattern is filed under one agent (the one with most failures), because c41 playbooks are per agent. A reviewer may find that odd; rejecting it costs nothing. A future change could allow an organisation-level candidate, but that touches c41's accept path, so it was not done here.
3. **Detection fields are write-once.** They can only be given when the tag is made (the table is append-only and c33's tags are decided once). To record a detection channel later, a person has to reject and re-tag. A separate append-only table for later detection entries would fix it; not in the brief. Detected-after measures to the moment of tagging (see above), so tagging late inflates it; no median or aggregate of it is shown, only per tag.
4. **Department is the current owner's.** A task whose failure came while an earlier owner held it is counted for its current owner's department. c6's department facts split ownership at handovers; this rule does not (stated in the code and the help).
5. **Mechanism and control lists are invented.** The brief names the fields but gives no values; the seven mechanisms and seven controls are my plain-words choices, frozen in shared contracts. If the owner wants different words, that is a new list version (the DB CHECKs would change with it).
6. **Window.** The recurrence window is fixed at 30 days (the `window_days` column allows 7, 30, 90 and the function takes `days`, but only 30 is evaluated). The window is rolling and keyed on the tag's creation time, the same as c33's counts, not on when the failure happened.
7. **UI placement.** The dialog went from lg to xl and the form sits in the left column under the modes. The "failure-modes view" of the brief is the counts row in this dialog (c33 has no other counts view). `failure.patterns` has a help entry but no UI control points at it yet (the list is API only), so there is no page where administrators see patterns except as lessons in Playbooks.
8. **Window of `failureModeCounts` changed** from `windowOf`'s app-clock Dates to SQL `now()` bounds (the Wave 5 clock rule). `from` and `to` in the answer are still the app-clock values for display. c54 (in review) may also touch this function.
9. **Connection cap.** Several runs (the first full vitest, a first api-e2e start, three coverage runs) failed with `too many connections for role "axion"` or `admin connect failed`; each was repeated and passed. No test was loosened.
10. No server of mine is running: ports 11190 to 11193 were checked free; the e2e DB axion_e2e12 holds the last browser run's data.
