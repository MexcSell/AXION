# c42 review (independent, adversarial): typed delegation brief and scope contract

Branch c42-delegation-brief, tip c3799eb (from c30 f483e2d). Read only. I ran `delegation-brief.test.ts` (13/13 pass). I did not run the E2E scripts.

Verdict: **NOT CLEAR**. Four Important findings. Two of them (I1, I2) break the cycle's own invariant or the simulator, and each has a small fix.

Line numbers refer to `server/src/delegation/service.ts` (S) and `brief.ts` (B) on the branch.

## Important

**I1. Stale descendant scope: a delegate can hold, and re-delegate, what its delegator no longer has (concern 4 is a real escalation).** S:84-89 and S:92-94 pick the parent as "the delegator's latest brief" and never look at the delegator's own ancestors. Example: root A holds [read, send_message]; B (child of A) holds [read, send_message]. The admin supersedes A's brief with [read]. B's latest brief is unchanged. B then delegates C [send_message]: it is checked against B's latest brief and accepted at depth 3. C holds a capability that its ancestor A now lacks, which is exactly the property the cycle says it guarantees ("no delegate ever holds a capability its ancestor lacked"). This is a revocation gap, not only a missing re-check. Fix: when resolving the scope of an agent, intersect it with the scope of its parent chain (walk `parent_brief_id` up to the root, take each link's latest brief), or reject a child brief whose ancestors' latest briefs do not cover it. At minimum the report must not say the invariant holds; the property test cannot see this (see M5).

**I2. A person can wedge the staffing simulator forever (concern 7: yes, the loop really does spin).** `staffing-sim.ts` step(): a thrown error is caught, logged, `more = true`, and the step is rescheduled every `stepMs`, with no cap and no backoff. The whole transaction (including the instance insert) rolls back each time, so the same error repeats. `attachSimBrief` (S:158-165) gives the manager a system root brief only if it has none, and then creates a child brief with the fixed caps [read, summarize] checked against the manager's latest brief. If a person has already POSTed a root brief (or a supersede) to the manager instance with a narrower scope, for example [read] only, then every later join throws 403 (S:103) and staffing never finishes. Both the POST route and the reassign route can create that brief while the mission is still in `planning` or `running`, because the instances already exist. The same applies to a human brief with a short future deadline (only the child's own deadline is checked, so not that one), but the scope case is enough. The simulator's `skipIfTooDeep` covers only the depth case. Fix: in `attachSimBrief`, catch `ApiError` (not DB errors) and skip the brief, or compute the child caps as the intersection with the parent's scope. Add a test: narrow the manager's brief mid-staffing, then assert staffing reaches `working`.

**I3. A child that omits a budget or deadline escapes the parent's limit.** S:110-115: the budget check needs both values (`parent.budget !== undefined && brief.budget !== undefined`), and the deadline check runs only inside `if (brief.deadline)`. A parent with deadline D and budget 100 can delegate to a child with no deadline and no budget; that child (and its descendants, since the parent's limit is never inherited) is unbounded. The spec says "a child deadline after its parent's → 400"; the intent is a bounded chain. Fix: when the parent has a deadline or budget, the child's missing value inherits the parent's (or is a 400).

**I4. Anyone who can see the mission can speak as an agent, or replace another author's brief.** routes.ts:30-33 and S:76-84. (a) `fromInstanceId` is accepted from any viewer, with no check that the caller may act for that agent. `from_id` is stored as the agent while `created_by` is the person. The delegate cannot exceed the agent's scope, so this is not a capability escalation, but a member who could not approve R3 can hand out an R3 kind that an agent holds, and the record says the agent did it. (b) `supersedes` has no author or role check. A root brief is re-checked against the caller, not the original author, so any member of a shared mission can replace an admin's root brief (and so the mission's whole "root grant set", S:92 fallback) with their own, narrower or different one. Fix: only an admin or the creator (`created_by`) may supersede; `fromInstanceId` should be admin-only or system-only. If the owner decides this is intended, say so in the help text.

## Minor

**M1. "Latest root brief of the mission" ignores whom it was addressed to (concern 3).** S:90: `parent_brief_id is null order by seq desc limit 1` takes the newest root brief for any agent, so an agent with no brief inherits the scope that was written for a different agent, and one new root brief changes every brief-less agent's scope at once. Prefer the root brief of the same `to_instance`, or an explicit mission grant row.

**M2. Origin handling is not monotone (S:30-35, B:12).** Origins are normalised with `new URL().origin` (host lowercased, path, port 80/443 and userinfo dropped) and compared exactly, which is correct and tested. But a person who cannot approve `origin-grant` is refused `read @ https://a.example`, yet may hold plain `read` with no origin, which covers every origin (B:43). The restriction is looser than the thing it restricts. Not a delegate-over-delegator escalation, but the human gate is inverted for origin-aware kinds.

**M3. Kind matching is exact, which is safe.** `trim()` then `hasOwnProperty` on the baseline: `Read`, ` read ` (trimmed to `read`), `__proto__` and `constructor` are refused or normalised. Duplicates are removed in the schema transform, so they cannot cause a violation or a double chip. No finding.

**M4. Re-rooting and the reassign route.** A human brief (reassign with `brief`, or the POST route without `fromInstanceId`) is always depth 1, so a person can reset an agent's depth and widen its scope up to what the person can approve. That is within the person's own authority and not an escalation, but it also overwrites a narrower brief set by an admin (any member of a shared mission, for R0-R2 kinds). Same root cause as I4(b). Note for the owner. A cross-mission brief is blocked: instances, tasks and the superseded row are all looked up with `mission_id` (S:65-80); the route checks mission visibility; tenant is carried. Good.

**M5. The property test is a pure-function test and cannot see the real bugs.** `delegation-brief.test.ts` property test: the chain is built with `scopeViolations` and then checked with an inline copy of the same predicate. It would catch a superset bug inside `covers` (the `refused > 20` bound stops an always-accept bug, and origin cases are generated), but it never exercises latest-brief selection, supersede, the root fallback or the DB path, so I1 passes unnoticed. Add an API-level case for I1 and I3, and a supersede-then-delegate sequence in the random model.

**M6. Concern 1 (optional person brief), concern 2 (no id link), concern 5, 6, 8.** Accepted as stated. Concern 1 is a real gap against "require or attach", honestly reported. Row-to-brief linking by mission, task and target is ambiguous when a task is reassigned twice to the same agent; adding `delegation_id` later is a migration. Help text correctly says the paper is conceptual.

**M7. Reassign form (missions.tsx).** Escalation and acceptance lines have no length limit in the UI (300 max, 3 min on the server), so the user gets a 400 toast only; add `maxLength` and a hint. `caps` starts as ['read'] and is sent even if the kinds list has not loaded or `read` were disabled. Buttons use `aria-pressed` and the chips carry text, and the group has a label and help, so accessibility is reasonable. The drawer card has a labelled `nav`, decorative icons are `aria-hidden`, and the checklist is a `ul`; the checklist boxes are non-interactive squares and read as checkboxes to a sighted user (they cannot be ticked). The tier colour is always paired with the tier text, good. I did not run fit-check; the report claims ALL FIT.

**M8. Concurrency.** `pg_advisory_xact_lock(hashtext('brief:'||mission))` is taken before every read of latest briefs, so two parallel briefs for one mission serialise and read each other's rows (READ COMMITTED sees the committed one). No race found; hash collisions only add contention.

## Checked and fine
- Time zones: `deadline` needs an offset, is normalised to UTC ISO, and both the past check and the parent comparison are done in SQL as timestamptz. No time-zone bypass.
- Append-only: UPDATE and DELETE trigger plus TRUNCATE trigger; the only exception is `axion.purge_demo = 'on'`, and the test proves it and the refusal otherwise. Cascade FKs only fire under the purge or a mission hard delete, which the trigger blocks.
- Depth cap: code constant, frozen, plus a DB check (1..3) and `(parent is null) = (depth = 1)`.
- `security.test.ts`: one line added to the write-route list and the route in `LIMITED_ROUTES`; nothing loosened.
- A person's root brief is run through `evaluate()` per kind, and again from the agent side (prohibited-for-agent kinds refused for everyone). Unknown kinds are 400.
- The cycle report's concern 7 states the risk but the code only handles the depth case; see I2.
