# c68 report: the operator attention queue, "Needs you" (R3-9) (lane w66, branch c68-attention-queue, from 24a8f05)

What the screen claims, and what it does not. It claims **navigation and traceability**: one list of what needs a person now, each row saying why it is listed and which check to run. It makes **no claim about fewer mistakes, safer approvals or less rubber-stamping**; no source shows that a "why" does that, and the 39% / 3% / 13.6% approval figures are unverified and not used. Nothing in the UI or the help text says otherwise (api-c68 checks every `?` text for safety and error-reduction wording).

## What was built
1. **Read model** (`server/src/attention/queue.ts`, `GET /attention`). Six row kinds, eight reason codes: pending approvals (by tier and age, the c58 records), stale task reviews (the c51 `STALE_BEFORE_SQL` rule), tasks waiting on a person past an expected time, confirmed failures with no detection channel (c63), org proposals and agent version proposals nearing expiry, lesson candidates awaiting review (including c63's system-derived ones, as their own reason). Every row has a reason code and a one-sentence `why` from a template (`why.ts`) over enums, numbers and system ids. A hostile approval title or detail never enters the sentence or the evidence (tested). Read only: nothing sweeps or expires (an approval past its expiry is simply not listed, and a test checks that nothing is written). All ages, distances and thresholds are computed in SQL with `now()`.
2. **Fixed ranking** (`rank.ts`, pure). Tier (R4, R3, R2, then every row without a tier in one band below R2), then the soonest expiry (a row that expires comes before one that does not), then the longest wait, then the id. **This order is a design choice, not a finding from a source**, and it has no effect on any decision or tier: the function takes only the list (no viewer, clock or database), and a test reads the source to confirm it imports nothing from the policy or approval code. An unknown tier fails closed (ranks with R4).
3. **Collapse** (`collapse.ts`, pure). Pending R2 approvals fold by mission and tier, stale reviews and waiting tasks by mission, failures by mode, lessons by agent and reason. Never by a person. **R3 and R4 approvals are never folded.** A row ranks by its best member. Every folded item stays listed under its row, the row count always equals its member list, and `totals.items = sum of counts`, `totals.collapsed = items - rows`. No alert budget, no suppression, no `LIMIT` (a test folds 210 failures of one mode into one row of 210).
4. **Three levels.** Each row carries Activity (its items), Action (label, route, `canAct` and the reason when not, by the same rule as the deciding route, e.g. `decideRefusal`) and Evidence (`evidence.ts`): the check that would expose a defect, with the stored facts. Approval: bound digest against the server-recomputed digest (the check says "DIFFER, so do not approve" when they differ) plus the three Rule of Two flags. Stale review: the attempt that was reviewed, the latest attempt, the freshness rule. Failure: the missing detection channel and the other detection fields as recorded or not. Org proposal: the revision it was made on against the active one. Version proposal: whether its base is still the active version. Lessons: sources cited and how the record was written; a system-derived one names its pattern.
5. **View** (`web/src/features/attention/NeedsYou.tsx`). A fifth Overview tab, "Needs you", after Pulse (Pulse stays the default). Ranked one-line rows (rank, icon, reason label and tier chip, templated why, count pill, expiry or wait, and a `?` per row as a sibling of the row button), a detail pane with Activity / Action / Evidence (the evidence is two clicks from the list), arrow keys and Enter, springs and fades like the rest of the app, live re-reads from the event stream plus once a minute, a labelled DEMO sample in demo mode (14 rows, 32 items), loading, error and empty states, and a stacked 390 px layout. One help entry per reason code, generated from the same table the server and screen use, plus entries for the ranking, folding and levels.
6. **Privacy.** Every loader applies its source route's rule: missions use `VISIBLE_SQL` (list, read and write use the same one), proposals are tenant-wide like their routes, lessons are admin or the person who made or filed them. Hidden items are not counted, so a member's folded count and totals are smaller than an administrator's. No name or id of a person appears anywhere in the response, and there is one route and no per-person variant. Policy decision (the brief left it open): **a member sees every visible item, including R3/R4 approvals and proposals they cannot decide, marked locked with the reason**, because the source screens already show them.
7. **Contracts.** DTO types in `shared/contracts/src/attention.ts`, a strict validator, a registry entry and a coverage call (admin and member). No allowlist lines. Migration 0051 was not needed.

## The ranking order (a design choice)
Tier, then soonest expiry, then longest wait, then id. Chosen because a person asked "what first?" is best served by the irreversible and the expiring. No source supports this order; the verifier said so and the help text for the `?` beside the header says so too. Rows without a tier (reviews, waiting tasks, failures, proposals, lessons) share one band between R2 and R1, which is also a choice. It changes no decision, tier or approval; a test compares the stored approval rows before and after a read.

## Collapse ratio on the 200-event fixture
`c68-collapse.test.ts`, "a fixture of 200 related events": 120 failures of 4 modes, 40 R2 approvals of 2 missions, 20 R3 approvals, 10 stale reviews of 2 missions, 10 proposals. **200 items become 38 rows, a 5.26 to 1 reduction; 162 items are folded under other rows, every one still listed, `sum of counts = 200`, `sum of (count - 1) = 162`, and all 20 R3 approvals keep a row of their own.** (An ordinary mix; the ratio depends entirely on how related the events are, so it is a property of this fixture and not a claim about real use.)

## Concerns
0. **What c58 data was reused.** The brief said to reuse c58's latency and queue data. The approval rows use c58's stored Rule-of-Two record and the same `decideRefusal` and `rowDigest` code as the deciding route, but **not** the latency, queue-size or fast-bulk records: those exist only for requests that were already decided, so they say nothing about a pending one, and the tenant-wide queue size would count approvals a member cannot see. A pending row's age is `now() - created_at` in SQL.
1. **The Company Health / Scorecard aside is not drawn on this one tab.** In api mode the scorecard makes the header about 316 px tall, which left room for only 9 rows. Without the aside the KPI tiles stay and 13 rows fit. It is a change to the shared header on one tab (`aside={tab === 'Needs you' ? undefined : ...}` in `Overview.tsx`), and the owner may prefer a different trade-off, for example folding the header.
1b. **The list scrolls inside its panel past about 13 rows.** `overview-fit.css` describes Overview as having no scrolling at all, not even inside a tab, and the other tabs show only the items that fit. This tab scrolls its list instead, on purpose: nothing may be hidden except by an explicit fold, so a "show what fits" count would drop rows. The page itself does not scroll (api-c68 and fit-check check it).
2. **A shared CSS rule changed.** `.tb-tabs > .tabs > .tab { flex: none }` in `frame.css`: with five tabs the labels were squeezed over their icons at 390 px. The strip now scrolls with its existing edge fade. It affects every page that uses TopBoard tabs.
3. **"Expected time" for waiting tasks is a fixed default (24 h), not an operator setting**, because there is no settings store for it. Tasks have no state-change time of their own; the read model uses the latest `task.stateChanged` event to `waiting_user`, and falls back to the task's creation time, which the evidence level says. Both thresholds (24 h waiting, 48 h to expiry) and the 30-day failure window are my choices, served in the response and written in the `?` texts.
4. **A confirmed failure leaves the queue in two ways only**: another confirmed tag on the same subject records a detection channel, or it is more than 30 days old. Detection fields are immutable after tagging (c63), so there is no way to fix the tag itself; otherwise it would stay for ever.
5. **Members see R3/R4 approvals and proposals they cannot decide** (locked, with the reason), as the source screens already show them. If the owner would rather members see only what they can act on, that is a one-line change per loader.
6. **Demo-mission rows appear in api mode** (the demo seed's approvals and tasks). Each member carries `demo` and the row shows a DEMO mark when every item in it is demo.
7. **Item 6 was not RED on unchanged code** (explained above); the mutation check is the evidence that the tests bite.
8. **Local numbers.** The one-row-per-folded-item response is bigger than the source routes' (210 failure items carry their evidence); fine at this scale, and the reason for no `LIMIT` is that nothing may be hidden. A very large tenant would need paging by row, not by item.
9. **Commit trailer.** The harness reminder asked for "Claude Sonnet 5.5"; LANES.md and the brief require "Claude Opus 5.5", which is what every commit uses.
10. The `a11y` dialog count (65 against c58's 66) is unexplained, see the table.
