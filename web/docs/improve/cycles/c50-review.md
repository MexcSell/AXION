## Confirmed findings

### F1 (medium, fix before or right after merge): `openObj` leaves mission and agent unchecked
`server/test/contracts/validate.ts` `openObj` casts its shape (`Record<string, V<any>>` to `Shape<T>`) and sets `open: true`. It is used for `mission` (`validators.ts:52`) and `agent` (`validators.ts:171`). `MissionDto` and `AgentStoredDto` do carry an index signature (`[presentation: string]: unknown`, `[profile: string]: unknown`), so openness is defensible, but two consequences are real:
1. No tsc tie. I added a throwaway `const b: V<MissionDto> = openObj<MissionDto>({ bogus: str })` and tsc accepted it; the same with `obj<HealthDto>` gave TS2353 (excess) and TS2741 (missing). So a key dropped from, or mistyped in, the mission/agent validator is silent. The report's claim "every validator is phantom-typed against the shared DTO" is false for these two.
2. Runtime: a mutation sweep over every node of every real 2xx body (extra key, key removed, key set to null) shows an extra key is accepted at only 11 routes, all of them mission or agent bodies: `GET/PATCH/POST /missions*` (`.mission`, `.phases[]`, `.staffing`, `.staffing.log[]/org/plan[]`), `/agents*` (`.agent`, `.agent.metrics`, `.agent.avatar`). `staffing`, `metrics`, `avatar`, `phases[]` are `unknownV`/`rec` passthroughs.
Scenario: the server adds `mission.priorityScore` or renames `agent.rowVersion` to something else only in the `[k: string]: unknown` slot; or someone deletes `rowVersion: int` from the validator; suite stays green.
Fix: type the known keys with a helper such as `Shape<Pick<T, KnownKeys<T>>>` (KnownKeys strips the index signature) so tsc requires every named key and rejects wrong ones; keep runtime open only for the index. Give `staffing` and `metrics` real validators or list them as a documented open area.

### F2 (low): the non-vacuity test cannot see F1 or nested strictness
`coverage.test.ts:356-374` adds one extra key at the body root (or `[0]` of an array) and removes the first key of an object body. It runs for every validator (not a sample, good) but only at the top level, and only the "extra" and "missing first key" mutations. For `{mission}` the wrapper is strict, so the open `mission` node is never tested. Nullability is not mutated at all. An empty-array sample is skipped silently (`target` undefined, no `lenient` entry). Event validators are only unit-tested through `guards.test.ts` for one type (`mission.shared`).
Fix: replace by a node-wide mutator (my sweep did exactly this in about 40 lines: extra key, drop key, null key at every object node, expect rejection unless the key is `opt` or `nullable`), applied to every route sample and every observed event.

### F3 (low): `gated` accepts any 403 with a valid envelope
`flow.ts:34` adds to `gated` for any 403 whose body fits the envelope. The member loop (`coverage.test.ts:294-300`) does not pin `code: 'FORBIDDEN'` (what `requireAdmin` throws, `session.ts:84`). A route whose 403 comes from another cause (CSRF, policy, `ACTION_NOT_ALLOWED`) would count as admin-gated. Risk is small: the placeholder id `x` means a route that lost `requireAdmin` returns 404 or 400, not 403, and fails. Pin the code and message anyway; it costs one line.

### F4 (low): `hits` is keyed by a hand-typed pattern
`call()` takes `pattern` and `url` as separate strings and never checks that they match. Many routes share validators (`okBody`, `missionBody`, `planBody`, `proposalBody`), so a copy-paste with the wrong pattern would credit a route that was never called. I checked the present file: 139 `call(` sites parsed, 0 pattern/url mismatches (the other 3 `call(` occurrences are the definition and prose). `POST /uploads` is credited by a manual `hits.add` (`coverage.test.ts:100`), which is legitimate (multipart) but is the one entry that does not go through `call()`.
Fix: in `call()` assert `new RegExp('^' + pattern.replace(/:[A-Za-z]+/g, '[^/]+') + '$').test(url path)`, or record the matched route from an `onResponse` hook (`req.routeOptions.url`).

### F5 (low): arrays and nullable fields the flow never populates
From the dump (112 array nodes and 197 leaves never non-empty or never non-null): arrays of objects that are always empty in every call, so their element validators never ran: `tasks/:id/reviews .evidenceOptions[]`, `delegation-briefs .briefs[].effective.narrowedBy[]`, `.mission.criteria[]` (all mission routes), `organization/*.result.errors[]`, `GET /organization/revisions/:seq/diff .removed[]`, `lesson.conflicts[]`, `playbook/diff .diff.removed[]`. Nullable fields never seen non-null include `canReview.code/reason`, `reviews[].reviewer.modelFamily`, `reviewerAgreement.rate`, `instances[].endedAt`. (Most other empty arrays are `string[]` where the element check is trivial.) The report concedes the general point; the list above is the concrete one. Seed one case each (a criterion on a mission, a blocked review, a conflicting lesson, an org dry-run error).

### F6 (informational): the emit scan has one computed site today, harmless
`inventory.ts` says "all emit sites pass a literal". Not quite: `server/src/auth/routes.ts:313` passes `type: action === 'approve' ? 'auth.approved' : 'user.changed'`. The regex `\btype: '...'` does not match it, but both literals are emitted elsewhere in literal form (`auth/routes.ts:253`, `:194` and others), so nothing escapes today. Other sites checked: `notifications/routes.ts:16` is a literal; `'skill.' + action` (`agents/playbooks.ts:460`) is an audit action, never an event type; no template strings or variables reach `emit` or `appendEvent`; `insert into events` exists only in `events/log.ts`. No other computed event type exists.
Durable fix (recommended, small): type `EmitInput.type` (`events/hooks.ts:5`) and `AppendInput.type` (`events/log.ts:8`) as `EventType`; tsc then rejects any undeclared or computed-to-string type and the regex scan becomes a belt only. This touches `server/src`, so it is a deliberate (non-behavioural) change for a follow-up, not a c50 blocker.

## Plausible, not confirmed
- P1: `registeredRoutes` strips `/api/v1` and dedupes, so a root-level route and a prefixed route with the same path would collapse into one key. No such pair exists today (all 108 are prefixed). An explicit `app.options(...)` or `app.head(...)` route is filtered out as well; none exists today (`onRoute` pushes HEAD twins only for GET).
- P2: `routeTable` is filled by an `onRoute` hook added on the root instance before any `register` (`app.ts:64`, plugins at 87-119), so plugin and prefixed routes are seen (confirmed: 108 entries, `/api/v1` prefix present; `app.get('/api/v1/health')` at `app.ts:123` registered after). A role matrix beyond admin versus member is out of scope for c50.

## Check-by-check answers

1. **Inventory soundness.** Sound. The table comes from the live app, includes plugin routes with prefixes; HEAD is dropped only because it is auto-generated; there are no explicit OPTIONS routes. 108 routes = 106 registry entries + 2 exclusions. The exclusions (`GET /events/stream`, `GET /uploads/:id`) are justified (non-JSON); the stream is covered by event validation, and the upload route is downloaded and byte-checked in the flow. A cap of 3 exclusions is enforced in `inventory.test.ts`. A registry entry cannot be a no-op: `v` is mandatory, and the closing test requires a 2xx call that passed `check()` for every entry (`hits`), which `call()` records only after validation. The one residual weakness is F4.
2. **Validator strength.** Strict on extra fields and on nullability for every node except the open mission/agent parts (F1). A 40-line node sweep (extra, drop, null at every object node of every real body) accepted an extra key at 11 routes, all mission or agent. `unknownV`/`rec` passthroughs: `mission.phases[]`, `mission.staffing` (via the open index), `agent.avatar`, `agent.updated.fields` (events.ts:30). Phantom typing verified with tsc probes for `obj<T>` and `EVENT_VALIDATORS` (mapped type); not for `openObj`. Spot-checked 10 validators against bodies and DTOs (health, ops health, audit verify, approval, notice, instance, task, task review, delegation brief, ledger): consistent, with `opt()` used where the DTO declares `?`.
3. **Admin flag.** Dynamic probe (not committed): every one of the 101 non-skipped routes was called as a member with placeholder ids. All 30 flagged routes returned 403 (positive control). The only unflagged 403 was `POST /tasks/:id/:action` with `ACTION_NOT_ALLOWED` (`tasks/routes.ts:51`: `start` is not a people action), which has nothing to do with role. No unflagged route is admin-only that I can see; the probe is inconclusive for about 45 unflagged routes that answered 400/404/422 to bogus ids. A static cross-check of `requireAdmin` per handler agreed with the flags for all routes (the only disagreements were my scanner's artifacts on `/skills`, where `decideSkill` is defined after `POST /skills`, which shows a static check is fragile). Recommendation: add the member sweep to the suite now, generated from the route table, as a required test: every registered route is called as a member (valid-ish ids from the flow, or the placeholder) and the set of routes that answer 403 `FORBIDDEN` must equal the set flagged `admin`; add the one-line `code: 'FORBIDDEN'` pin from F3. It is about 30 lines and the registry already provides the call list. Treat a flagged route that does not answer 403 as a test failure (that already happens in the flow loop).
4. **Event scan.** See F6. No computed event types exist that escape detection today.
5. **Drift fixes.** `approval.consumed` is correctly added: `EVENT_TYPES` now lists it, with payload `{approvalId, kind, tier, by}` matching `approvals/service.ts:140`. `git diff --stat bd64f37..45d984c -- server/src` is empty: no server code changed. `POST /agents/:id/rollback` already returned `{agent, version}`; only the contract/validator was wrong. It is a contract-side correction, not a behaviour change, but the report should say plainly (it does, under "Drift found" item 2) that the server was already returning `version`. `EventType` changed from a union to a derived type with the same members plus `approval.consumed`; web tsc was reported clean and no web code changed.
