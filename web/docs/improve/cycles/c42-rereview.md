# c42 re-review (fix tip 85bf2e3, after first review at c3799eb)

Verdict: NOT CLEAR (one Important: the staffing give-up is a silent stall). vitest delegation-brief.test.ts re-run: 23/23 pass.

## Findings

1. Important. `server/src/missions/staffing-sim.ts` catch block (`if (n > 12) { app.log.error(...); fails.delete(id); return; }`). After 12 consecutive failures the step returns without rescheduling, and the only trace is a log line. The mission stays `planning`/`running` with `staffing.stage` short of `working`, no event, no audit row, no status change, no notification. Nothing revives it: `onMissionChanged` is only called on user actions and the 60 s sweep only touches expired approvals, so it stays stuck until a server restart (the resume query then reschedules it, and it fails again if the cause persists). The rule was "a silent stall is a defect". Needed: at give-up, write an audit row and emit an event (for example `staffing.failed`), or set a visible state on the mission, so the UI can show it and an owner can retry. Backoff itself is fine: per mission (`fails` map keyed by id), reset on success (`fails.delete(id)` after a good step) and capped at 30 s (total wait about 5 minutes before giving up).

2. Minor. `server/test/delegation-brief.test.ts` M5 (about line 355). The invariant checks `b.effective`, which `effectiveFrom` builds as an intersection with every ancestor, so it holds by construction. Against the old code it went RED only because the `effective` field did not exist, not because it detected the I1 hole. It would not catch a regression in the creation gate (`createBrief` checking raw `parent.brief.capabilities` again), because the effective output would still be intersected. Add an assertion on every accepted 201 that the stored `brief.capabilities` is a subset of the delegator's effective scope computed just before the post. The deterministic I1 test (line 221) does catch the attack, so this is not blocking.

3. Minor. No test for an admin from another tenant. By reading, it is safe: `visibleMission` in `server/src/delegation/routes.ts:17` filters on `m.tenant_id` and returns 404 before `createBrief` runs. The tasks/routes reassign path uses `visibleTask`, which I did not trace.

4. Minor. `server/src/delegation/service.ts:91` supersede needs the author or an admin, so a mission owner (non-admin) cannot supersede a simulator (`created_by='system'`) brief. The owner can still post a fresh root brief for the same agent (no `supersedes`), which becomes the latest and also re-widens a root that someone narrowed, within the owner's own authority. That is consistent with the rulings (the owner may write roots), but note that "narrowing" can be undone by the owner, and a new root for a mid-chain agent re-roots it and drops its ancestor limits.

## Checks

1. I1 holds.
   - `createBrief` takes `pg_advisory_xact_lock` on the mission (service.ts:74) before the `missionRows` read (about line 82). The lock is held to commit, default isolation is READ COMMITTED, so the effective-scope read and the insert are serialized with narrowing and supersede (which also go through `createBrief`). Concurrent narrowing vs child creation is safe.
   - `effectiveFrom` resolves each ancestor to that agent's newest brief and intersects up to the root, so narrowing the root after a grandchild exists is applied at once. Superseding a middle link wider than its parent is refused at creation (the parent's effective scope is the bound), and even a wide row would still be intersected on read.
   - A cycle (A to B to A) is cut by the `seen` set; the loop is bounded at `MAX_CHAIN_DEPTH+1`. A chain at the cap of 3 works (depth test) and depth 4 is 400.
2. I2 partial. The savepoint catches only `ApiError`; database errors propagate. Each skip is audited as `delegation.brief_skipped` with the reason, and the test checks the audit row and a usable transaction. The sim child caps are intersected with the manager's effective scope. A skip that rolls back also removes a freshly created sim root, which is retried on the next join. Defect: finding 1.
3. I3 holds. The effective deadline and budget are the minimum along the chain. Deadlines are normalised to UTC ISO with milliseconds by the zod transform, so string comparison is valid, and the creation comparison is done in SQL with `timestamptz`. A missing value inherits the bound, an explicit higher value is 400, and the test covers three levels plus narrowing afterwards. An expired inherited deadline makes child creation 400 (PAST); the simulator skips and audits that case.
4. I4 holds. The rules are root and speaking-as-agent need admin or the mission owner, supersede needs the author or an admin, and a replaced root is also checked against the original author's role (the narrower wins). A member of a shared mission can read but gets 403 on write (tested). `POST /tasks/:id/reassign` only reaches `createBrief` when a `brief` is sent, which api-stage6 does not do, so that script is unaffected; a member who sends a brief now gets 403, but the brief is new in c42, so no earlier behaviour broke.
5. M2 is consistent. `covers` requires the same kind and the same origin (undefined equals undefined). The human gate, `rootViolations`, runs `evaluate` per kind and adds the `origin-grant` check for any capability with an origin. Origins are normalised by `new URL().origin`, so case and path differences collapse (tested with `https://A.example/x`).
6. M5: see finding 2.
7. Nothing loosened: M1 removed the root fallback, M2 removed the origin wildcard, and the new checks add refusals only. The `canApprove` change is a syntax fix (a semicolon after a comment), not a behaviour change.
