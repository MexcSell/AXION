## 3. Candidates

Code facts that matter (read-only):
- `delegation_briefs.brief` JSON carries optional `taskClass` and `difficulty` (brief.ts line 28, delegation.ts line 8), set by whoever delegates (metric-guard.ts). Briefs without them are not usable for adjustment; skills.ts already counts only finished tasks whose brief names both. Brief rows are append-only with `created_at`, a `sha256`, and an `escalation` string inside the brief.
- `tasks` has `created_at` only (no done time, no status-change time). Attempt times are in `task_attempts.started_at/finished_at`; review verdicts and times in `task_reviews` (`accepted | changes_requested | rejected`, `created_at`, append-only). Final states are `passed`/`failed`.
- `org_revisions` are tenant-wide (`seq`, `note`, `active_from`) with edges per revision; there is no per-team "treated unit" record. Proposals already store a free-text `baseline` and `expectedCost` (20-1000 chars) inside `payloadSha` (c64), so a hash-locked proposal payload exists.
- `evolution/stats.ts`, `agents/skills.ts` already provide Wilson intervals, a not-enough-evidence floor (`SKILL_MIN_N = 5`) and no-leaderboard rating; no code for Brier, conformal, permutation, placebo or confidence sequences, and no forecast, hypothesis or handoff table exists.
- No agents execute, so outcomes come only from human-entered or fixture work. Volume is demo-scale.
