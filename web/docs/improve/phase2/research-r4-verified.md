### R4-2: does the chain allow redaction without breaking verification?

No, not as built. `detail` is hashed directly in plaintext inside `canonical(row)`.

- Overwriting or removing `detail` on a row (after bypassing the UPDATE trigger) makes `verifyChain` fail at that row with "row content does not match its hash". Later rows still carry `prev_hash` equal to the stored `row_hash`, so the walk fails exactly at the first redacted row and stops there (it stops at the first bad row). One redaction therefore makes `GET /audit/verify` red for the whole tenant.
- Rehashing from that row forward would restore verify but changes every later `row_hash`, which c49 reports as `rewritten`, and the anchor file cannot be re-signed without the key. So history cannot be repaired in place.
- Only `detail` could be redacted. `actor`, `subject`, `action`, `result`, `correlation_id` are also hashed plaintext and cannot be tombstoned by the proposed scheme; if they can hold personal data the scheme is incomplete (the brief must say which columns count as payload).
- The file's note that the chain head does not change on redaction is true only for a v2 chain where the hash commits to a salted commitment. The existing 0026 backfill and every existing row would need a v1/v2 distinction in the verifier, in the SQL twin, in the anchor interplay (v1 rows stay anchored as today), in the OTLP export, and in the trigger guards (the salt and tombstone tables need all four guards).
- Per-record salt stored in the same database gives erasure of readable payload only. A1 para 52 sets conditions (key not compromised, salt not leaked), and a database operator can read the salt before it is destroyed and any backup holds it. The file states this limit; keep it prominent. Backups (`db-backup.sh`) also hold the payload; threshold (d) must include them or say they are out of scope.
- Verdict: the mechanism is sound as a design for new rows on a new chain version; it is not a 4-6 hour lane and not a today item. A design-only brief, with the redactable-column list and the v1/v2 verification rules, is the right first step. Do R4-6 first, as the file says.
