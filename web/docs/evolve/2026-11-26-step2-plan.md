# Evolution step 2 (Workshop) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An owner request becomes an AXION mission of kind `improve`; a host runner has an engineer agent (Claude 1) change the code in a
Workshop container, checks and reviews the diff, hands the commit to `axion-guard deploy`, and mirrors every step into the mission.

**Architecture:** App side: a new mission kind `improve` (admins only), a mission page that shows the change's progress and report, and
one CLI inside the app image (`server/src/cli/evolve-missions.ts`) through which the host runner reads and writes missions (run as
`docker run --network none` from the live image on the DB socket, so it always matches the live schema). Host side (protected, under
`evolve/`): the Workshop image, the engineer/reviewer runs, diff gates (protected paths, secrets, static flags), and the runner loop
(`axion-evolve`, a systemd service) that calls the existing Guard.

**Tech Stack:** Node 24 (native TS stripping for `evolve/`, `node --test`), TypeScript server (vitest), React web, Docker, Claude CLI
2.1.325 (OAuth token `CLAUDE_CODE_OAUTH_TOKEN1`).

**Spec:** `web/docs/evolve/2026-11-26-autonomous-evolution-design.md` (approved; §7.2, §7.4, §8 step 2, §13 B1, B5, B8). Step 1 code
and report: `evolve/`, `web/docs/evolve/step1-report.md`.

## Global Constraints

- Engineer and reviewer use **Claude 1 only** (`CLAUDE_CODE_OAUTH_TOKEN1`); the live slots and chat keep Claude 2 only. TOKEN1 is never
  written to the image, git, logs, mission text, or any file other than `/srv/axion-evolve/secrets/workshop.env` (mode 600).
- The Workshop container: never the Docker socket, never the DB, never a host mount except `/srv/axion-evolve/work/<change>`; network
  `axion-workshop` (`--internal`, inhibit_ipv4 like `axion-live`) whose only way out is `axion-egress` (allowlist `api.anthropic.com:443`).
- Claude CLI flags for every Workshop run: `-p --model <m> --output-format json --setting-sources "" --strict-mcp-config
  --disable-slash-commands --no-session-persistence --permission-mode dontAsk --settings <json>`, tools exactly
  `Read,Edit,Write,Glob,Grep` for the engineer and `""` (none) for the reviewer. No Bash, no web tools. The settings JSON denies
  Edit/Write on every `evolve/protected.txt` pattern and Read/Grep/Glob on `/proc/**`, `/etc/**`, `/srv/**`, `/root/**`, the
  container's HOME and `/tmp` (two layers: tool level + Guard classify on the diff). The absolute-path rule syntax is verified against
  the real CLI in the Workshop image (Task 3 step 3), not assumed.
- Agent-written code runs only in no-network, no-token containers: the runner's pre-push typecheck (Task 4) and the Guard's checks.
  Never in the Workshop (it has no Bash).
- **The Workshop never sees a git directory.** It gets an exported tree (`git archive`) at `/work`; the commit is built by the runner
  from a runner-owned git dir (`-c core.hooksPath=/dev/null -c core.fsmonitor=false`, no filters), so nothing the engineer writes is
  executed by root. Edit/Write on `**/.git/**`, `.git*` and `**/.gitattributes` are also denied at the tool level.
- An agent change that hits a protected path is **never** auto-approved: the mission ends "needs the owner" with the hit list.
- The Guard is used unchanged through its CLI (`axion-guard deploy incoming/<ref>`; exit 0 live, 1 rejected/rolled back, 3 needs owner,
  4 busy; JSON result line on stdout).
- Caps (constants in `evolve/runner/config.ts`): attempts per change 3; engineer wall time per attempt 30 min; reviewer 5 min; changes
  per UTC day 12; 2 consecutive rolled-back changes → the runner pauses itself (writes `/srv/axion-evolve/PAUSED`).
- Kill switches checked before every step: file `/srv/axion-evolve/PAUSED`, or a run halt (`run_halts`, tenant `t-1`) with
  scope `global` or (scope `class`, target `evolution`) whose newest row has `halted=true`.
- Only missions of kind `improve`, status `running`, created by a user with role `admin`, are picked up. Members cannot create kind
  `improve` (server refuses with 403).
- Mission status follows the state machine (`server/src/missions/machine.ts`) with system actions only: `running →verify→ verifying
  →complete→ completed`; `fail`; a protected/flagged change goes `running →requestApproval→ waiting_approval` with its commit kept
  at `incoming/evolve-<id>-a<n>` and the exact approve command in the mission; `axion-evolve approve <mission>` (Claude Code / the
  owner) deploys it with `--approve` and then `approvalDone → verify → complete` (or `fail`). Nothing ever auto-approves.
- The runner writes `presentation` only under the mission row lock (`select … for update`, then merge), and claims a mission only once
  its staffing is finished (`presentation.staffing.stage = 'working'`), so it never races the staffing simulation.
- Existing event types only (`staffing.progressed`, `mission.stateChanged`): no change to `EVENT_TYPES`. No migration.
- No GitHub push. Names use the `axion-` prefix. Commits in the Workshop are authored `AXION engineer <engineer@axion.invalid>`.

## Review Focus

1. A prompt-injected mission text tries to make the engineer exfiltrate TOKEN1 (write it into a file, the commit message or its
   report): the secret scan must reject the change before any push, and the mission must not show the value.
2. The runner is restarted mid-change (crash, reboot): the claimed mission must not stay "working" forever nor be done twice.
3. The engineer makes no change, or only touches protected paths, or its run times out: the mission ends with an honest reason and
   nothing reaches the Guard.
4. The Guard answers busy (exit 4) or rejects at `checks`: busy waits and retries; a check failure is fed back to the engineer for the
   next attempt with the failing part of the log, up to the attempt cap.
5. A member (not admin) sends `improve: true`, edits a mission's kind to `improve`, or edits the text of a shared admin-owned
   `improve` mission: the kind changes are refused, and the runner picks a mission only when the claimed revision's `created_by` is an
   admin (a member's text edit makes it ineligible).

### Task 2: `server/src/cli/evolve-missions.ts` — the runner's door into missions (app, protected)

Run as `node --import tsx server/src/cli/evolve-missions.ts <cmd>` with `DATABASE_URL` set; prints one JSON line; exit 0 ok, 1 error,
2 usage. Uses the existing service functions (`appendEvent`/`emit`, presentation patch with `row_version+1` like `staffing-sim.ts`, CAS

**Interfaces (produces, used by Task 4):**
- `halted` → `{halted: boolean, reason?: string}` (global, or class `evolution`)
- `recover` → marks every mission whose `presentation.evolve.state` is `claimed|working|checking|deploying` as failed with reason
  "interrupted (runner restarted)"; `{recovered: string[]}`. (Guard state is the truth for what is live; the runner calls this at start.)
- `next` → claims (CAS on `row_version`) the oldest eligible mission (kind `improve`, status `running`, owner role `admin`, no

  `{at, by, text}`, merges `presentation.evolve`, sets `summary`/`lastEvent`, emits `staffing.progressed` `{evolve: true}`

## Departures from the design (rulings, each with its cost if wrong)

- No scrubbed live-data copy in the Workshop (§7.2): the engineer has no Bash and no DB; it reads migrations for data shapes.
  Cost: changes that depend on real data shapes are weaker; added in step 3 if needed.
- Protected/flagged agent changes do not create a row in AXION › Approvals (its digest/policy code is protected and complex): the
  mission goes `waiting_approval` with the exact approve command. Cost: the owner approves from the mission text, not the Approvals page.
- No tamper-detector pass over the Workshop's steps (§7.3 step 4): the engineer has no Bash, so there are no commands to judge; the
  diff gates + reviewer + Guard checks stand in. Cost: a pattern the static flags miss is caught only by the reviewer or the checks.
- GM chat drafts still get their kind from `guessKind`; only an admin's explicit "Improve AXION itself" creates kind `improve`.
  Cost: an owner request typed in the chat needs one extra tick in the create dialog.
